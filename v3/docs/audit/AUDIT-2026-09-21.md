# Audit — BOHO IMPORT BOM/THDM — 2026-09-21

## Summary

Stack: Python 3.14 (target-version py310 in ruff config), CustomTkinter GUI, pandas/openpyxl for Excel, pyodbc → SQL Server (Bravo ERP). `requirements.txt` unpinned except `Pillow>=10.0`. No `pyproject.toml` build backend — it only carries `[tool.pytest.ini_options]` and `[tool.ruff]` config.

Tests: **115 passed / 5 failed / 2 skipped** (122 collected, pytest 9.1.1, Python 3.14.6) — was 22/22 passing on 2026-08-03. Suite grew ~5.5x but now has real failures.
Ruff: **149 issues** (was 170 on 2026-08-03) — net improvement, but composition changed (see below).
Gaps found: 11 (4 critical/high, 4 medium, 3 low)

## Findings

### CRITICAL

**1. Undefined name `_DATE_FMTS` in `Tools/views/main_window.py:9024` and `:9278` — NameError on this path at runtime.**
`_DATE_FMTS` is defined only in `Tools/services/validators.py:27`. `main_window.py:61-64` imports `validate_layer1, count_errors, REQUIRED_HEADER_FIELDS, NUMERIC_RE` from `services.validators` — `_DATE_FMTS` is not among them and is not otherwise defined/imported in `main_window.py`. Both call sites (`for fmt in _DATE_FMTS:`) will raise `NameError` the moment that date-parsing fallback branch executes. Confirmed via `ruff check --select F821` (2 hits) and manual grep — no local or imported binding exists.
Evidence: `Tools/views/main_window.py:9024`, `:9278`; definition only at `Tools/services/validators.py:27`.

**2. Connection leak on exception path, `_get_db_conn()` call sites — reproducible, current.**
`Tools/views/main_window.py:8213` defines a single centralized `_get_db_conn()` helper (good — old audit's "connections created ad hoc throughout" is now consolidated to one function). However all 28 call sites (`grep -c "_get_db_conn("` = 28) call `.close()` only on the success path, none use a `with` statement (`with self._get_db_conn(` → 0 matches) or a `try/finally`. Concrete example: `Tools/views/main_window.py:2444-2457` — `conn.close()` is on line 2454, reached only if `cur.execute()`/`cur.fetchall()` succeed; the `except Exception as e:` at line 2456 does not close `conn`. Any exception between connect and the success-path close leaks the connection.
Evidence: `Tools/views/main_window.py:2444-2457` (representative), 28 total `_get_db_conn(` call sites, 0 `with`-statement usages.

**3. Core parser snapshot tests are failing against production-derived fixture — regression or stale fixture, unresolved.**
`tests/test_parser_snapshot.py::TestParserValid::test_meta_has_required_fields` and `::TestValidatorValid::test_zero_errors` both fail against `tests/fixtures/bom_valid.xlsm` (the designated "known-good, must pass with 0 errors" fixture):
```
AssertionError: Meta thiếu các field bắt buộc: ['Mã sản phẩm', 'Dự án', 'Đơn hàng']
AssertionError: File hợp lệ không được có lỗi. Tìm thấy 2 error:
  [[H] Phiếu Header] row=Header col=Mã sản phẩm: ...
```
This directly touches header/meta parsing and the DETAIL label-mapping area that commits `feda97e` (v2.2.21) and `6beb486` (v2.2.20) just changed ("sua label mapping DETAIL"). Either those commits regressed header-field recognition for the standard fixture, or the fixture is now stale relative to the mapping file — both are live-tool-correctness risks and neither has been resolved since these commits landed.
Evidence: `tests/test_parser_snapshot.py:48-52`, `:76-85`; fixture `tests/fixtures/bom_valid.xlsm`.

**4. DB integration tests fail against live schema/SPs (ran this session — VPN was reachable).**
`tests/test_db_integration.py` is `pytestmark = pytest.mark.integration` (skips cleanly if DB unreachable) but it *connected successfully* this run and found:
- `TestDBConnectivity::test_bom_table_has_expected_columns` — B20BOM table is missing column `ItemId` (actual columns include `ItemId0` instead — possible unintended rename/drift, notable given `9dc3c92` (v2.2.22) just touched `B20BOM`/`EmployeeId` handling).
- `TestStoredProcedures::test_required_sps_exist` — `usp_sys_AutoNewCode` does not exist or is not accessible from the test DB context.
- `TestFullPipeline::test_parse_validate_passes` — fails downstream of finding #3 (2 validation errors on the fixture).
Evidence: `tests/test_db_integration.py:137`, `:333`, `:355`.

### HIGH

**5. F-string/interpolated SQL still present — 34 sites in `main_window.py`, 1 in `bom_parser.py`.**
Old audit flagged this as "SQL Injection Vulnerability in Schema Detection" (`main_window.py:4299, 4371`). It is not fixed — count is now higher and the pattern is widespread, e.g. `Tools/views/main_window.py:2946` (`f"SELECT DISTINCT [{_cv}] FROM [BOMTool].dbo.vB20Item "`) and `:3189`/`:3210` interpolate `col_key`/`code_col` directly into SQL text. Most values appear to originate from schema/mapping metadata rather than direct end-user free text, but there is no visible whitelist/validation step before interpolation, so the mitigation the old audit assumed ("fragile if input validation is missing upstream") is still unverified.
Evidence: `Tools/views/main_window.py` — 34 f-string-SQL lines (script-counted), representative at `:2694, :2706, :2905, :2912, :2946, :3189, :3210, :3392`; `Tools/services/bom_parser.py` — 1 site.

**6. `tests/test_db_integration.py` is scoped as `integration` but ran (and failed) in a default `pytest` invocation.**
The audit task's own suggested invocation (`python -m pytest --tb=short -q`) does not deselect `-m "not integration"`, so DB-dependent tests execute whenever a developer has VPN on, silently mixing environment-dependent failures into what should be a fast offline suite. `pyproject.toml`'s `addopts` does not exclude the marker by default. Not a bug per se, but it explains why "tests pass/fail" is not a stable signal across machines — flag as a CI/workflow gap.
Evidence: `pyproject.toml` `[tool.pytest.ini_options]` — no `-m "not integration"` in `addopts`; `tests/conftest.py:30-34`.

## Changed since last audit (2026-08-03)

**Fixed:**
- **Bare `except:` clauses eliminated in production code.** Old audit: 416 in `main_window.py` + 41 in `bom_parser.py`. Current: **0** in both files (verified via regex scan + direct `grep -n "except:"` — both return 0 matches). Exception handling now uses typed `except Exception as e:` (or narrower) throughout scanned files.
- **`Tools/services/bom_parser.py` tkinter import guard added.** Lines 21-28 now wrap `import tkinter as tk; import customtkinter as _ctk_mod` in `try/except ImportError`, setting `_HAS_TK = False` on failure — code comment `# A1: guard — bom_parser chạy được không cần GUI` indicates this was a deliberate fix. Old audit's "missing guard" concern is resolved.
- **DB connections centralized.** Old audit described `pyodbc.connect()` scattered "throughout" `main_window.py`. Now there is exactly one connection-construction function, `_get_db_conn()` at `main_window.py:8213`, called from 28 sites. Centralization improved, but the leak-on-exception pattern persists within that single function's call sites (see finding #2) — the underlying risk moved from "many connect call sites" to "one connect helper, no context-manager discipline at call sites."
- **Automated test suite exists and is substantial.** Old audit: "only three manual test scripts... no automated test suite." Now: 122 pytest tests across 6 files (`tests/test_bom_parser.py`, `test_db_integration.py`, `test_parser_snapshot.py`, `test_sheet_detection.py`, `test_utils.py`, `test_validators.py`), plus fixture infrastructure (`conftest.py` with VPN-aware skip logic, transaction-isolated DB tests).
- **Ruff issue count dropped 170 → 149** (net -21, -12%), though composition shifted (see finding #10) — real remaining issues are far fewer than the raw count suggests once E701/E702 style noise is set aside.

**New / regressed:**
- **New `F821` undefined-name bug** (`_DATE_FMTS`, finding #1) — not present in the 170-issue 2026-08-03 baseline categories cited in AUDIT_PLAN.md; introduced at some point in the last 7 weeks of `main_window.py` edits.
- **Parser snapshot tests now fail against the "good" fixture** (finding #3) — did not exist as a signal on 2026-08-03 (tests didn't exist yet), but represents an active, currently-broken invariant ("standard file must parse with 0 validation errors") coinciding with the v2.2.20/v2.2.21 DETAIL label-mapping commits.
- **`main_window.py` grew +15%** (9,667 → 11,115 lines) — the monolith concern is actively worsening, not stabilizing.
- **Credentials handling unchanged and still correct**: `Tools/config/db_config.json` and `Other/acc.txt` both exist on disk, both remain gitignored (`.gitignore:19,21`), both confirmed absent from git history (`git log --all --full-history` for each returns empty, `git ls-files` returns empty). No regression, no improvement needed here.
- **CI/CD**: still absent. No `.github/workflows`, `.circleci`, or `azure-pipelines.yml`. Unchanged from 2026-08-03.

## Recommended priority order

1. Fix `_DATE_FMTS` NameError (finding #1) — trivial one-line import fix, currently a live crash-on-use bug. `from services.validators import ..., _DATE_FMTS` or make it a shared constant in `services/utils.py`.
2. Investigate the two failing parser-snapshot tests against `bom_valid.xlsm` (finding #3) — determine whether v2.2.20/v2.2.21 mapping changes broke header-field recognition, or whether the fixture needs regenerating. This blocks trusting the "0 errors on valid file" invariant that the whole validation layer depends on.
3. Wrap `_get_db_conn()` call sites in `try/finally` (or add a context-manager wrapper method) to stop the exception-path connection leak (finding #2) — 28 call sites, mechanical fix.
4. Reconcile `B20BOM.ItemId` vs `ItemId0` and confirm `usp_sys_AutoNewCode` existence/permissions with the DBA (finding #4) — could be an environment-specific issue (test DB vs prod) or a real schema drift; needs a human with DB access to confirm before deciding priority.
5. Split `pytest` invocation so default CI/local runs exclude `-m "not integration"` (finding #6) — makes "tests pass" a stable, VPN-independent signal; one-line `addopts` change.
6. Pin `requirements.txt` versions (finding #9) — increasingly urgent now that Python 3.14 is in play.
7. Audit the 34 f-string SQL sites in `main_window.py` for any path where the interpolated value could originate from user input rather than fixed schema/mapping metadata (finding #5) — lower urgency if all sources are confirmed schema-derived, but currently unverified.
8. Longer-horizon: begin extracting logic out of `main_window.py` (findings #7, #8) — coverage and file-size trend are both moving the wrong direction; every new feature commit adds to a file with zero tests.
9. Housekeeping: delete or move the 7 dead `main_window_backup*.py` copies and the 3 backup/archive directories (~603 MB) out of the working tree (finding #11) — no functional risk, but reduces search/discoverability hazard.
